Four tools, four different jobs

  • VS Code: where we edit and inspect files
  • Git: records change history on our computer
  • GitHub: hosts shared repositories and reviews
  • Azure: runs our apps and cloud resources

Edit locally → collaborate on GitHub → run in Azure

3–6 minutes. Git works without GitHub or an internet connection. GitHub is not Azure, and saving a file in VS Code does not update a running app. Azure is Microsoft's cloud platform. Azure DevOps is a separate collaboration and pipeline product; use the actual company delivery tool when demonstrating.

Git: a shared project with a memory

  • Repository (repo): project files plus their history
  • Clone: make a local copy of a repository
  • Branch: a separate line of work
  • Commit: a recorded snapshot with a message

Think: shared project folder + checkpoints + parallel work

6–9 minutes. A branch lets us work without immediately changing the shared main branch. Show one small change and its commit message rather than a complex branching diagram. A commit records the staged changes, not automatically every file.

Local is not the same as shared

Save → Stage → Commit → Push

  • Save: update the file on your computer
  • Stage: choose changes for the next commit
  • Commit: record those changes locally
  • Push: send local commits to GitHub
  • Pull: bring remote changes into your branch
9–12 minutes. Ask: “If I commit but do not push, can my colleague see it on GitHub?” Answer: no. Fetch checks for remote updates without integrating them; pull integrates them. VS Code Sync can pull and push, so demonstrate the separate actions first. If a conflict appears, do not blindly accept a version: inspect both changes, agree the intended result with the author, test, then commit the resolution.

The everyday VS Code workflow

  1. Clone the approved repo and open its folder
  2. Start from an up-to-date base; create a work branch
  3. Edit, save, and check the result locally
  4. Review the diff; stage and commit your change
  5. Publish the branch / push, then open a pull request

Explorer = files · Source Control = changes · status bar = branch

12–15 minutes. Briefly point out Explorer, editor, Source Control, and the branch indicator; leave the actual clicks for the demo. Git must be installed as well as VS Code. Use Git: Clone from the Command Palette and company-approved sign-in. Open only trusted repositories; review Workspace Trust prompts before trusting. Check for uncommitted work before switching branches or pulling. Run the repository's documented checks. A diff is the before/after comparison. Git operations are built in; the GitHub Pull Requests extension is optional, and the browser is sufficient for opening and reviewing a pull request.

How code reaches Azure

Branch → Pull request → Checks & review → Merge
→ Build → Deploy → Verify

  • Pipeline: automated steps that check and deliver code
  • Build: prepare the version that will run
  • Deploy: release that version to an environment

GitHub stores code; Azure runs the deployed version.
A push or merge only deploys if a configured pipeline triggers it.

17–19 minutes. This is a simplified example, not a guarantee of our release sequence. Use our actual pipeline, whether GitHub Actions, Azure DevOps, or another approved tool. Explain checks as an automated safety net and approvals as a human decision. Production may require a separate release. Pipeline authentication uses an approved identity with limited permissions; never display credentials during the demo.

Live demo: one small, visible change

Example: change the welcome heading in an existing demo web app.

  1. VS Code: clone, branch, edit, preview, diff, commit, push
  2. GitHub: open PR, inspect checks, review, merge
  3. Pipeline & Azure: follow deployment and verify the app

Success = the reviewed change is visible at the test URL.

20–50 minutes. Use an existing approved sample app already connected to a working non-production deployment pipeline, not this presentation site's GitHub Pages deployment. No new infrastructure setup during the meeting. 20–30: show the repo URL, clone/open it in VS Code, pull the clean base branch, create a branch following our naming rule, and change only the welcome heading. Save and run the app's documented preview/checks. Inspect the diff, stage only the intended file, commit with a descriptive message, and publish/push. 30–40: open GitHub, create a PR targeting the approved base, describe the change and verification, show Files changed and check results, and request review. Have an authorized colleague ready to review. Address feedback, wait for required checks, then let an authorized person merge; never bypass protections for the demo. 40–50: follow the configured pipeline trigger or approved manual release, show the run for the merged revision and any environment approval, and open the Azure resource and test URL. Confirm the deployed revision and visible heading. If checks fail, inspect the failing step and fix via the same branch/PR workflow. If deployment fails, stop promotion and use the documented recovery process. If a run is slow or access fails, use a previously completed approved demo PR/run and sanitized screenshots, clearly labeled as a recorded example. Do not pretend a queued or failed run is a successful deployment.

The workflow to remember

Get latest → Branch → Edit → Check → Commit → Push
→ Review → Merge → Deploy → Verify

  • A saved file is not a commit; a commit is not a deployment
  • Small changes are easier to understand and review
  • Follow our rules and ask for help when unsure
